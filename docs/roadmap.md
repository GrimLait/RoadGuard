# План розробки системи «RoadGuard» (Epic & Story Map)

Цей документ визначає послідовність інкрементальної розробки системи RoadGuard, розбиту на логічні етапи (Epics) та користувацькі історії (User Stories).

---

## 1. Загальна карта епіків (Epic Map)

Розробка ведеться інкрементально за такою черговістю:

* **Epic 1: Базова інфраструктура та автентифікація** — Каркас монорепозиторію, Docker Compose, база даних PostgreSQL та реєстрація/вхід користувачів із фіксацією згоди на донавчання ШІ.
* **Epic 2: Інтерактивна карта дефектів та гостьовий режим** — Інтерактивна карта (Leaflet), відображення публічних міток дефектів та демонстраційний режим детекції для Гостя.
* **Epic 3: Модуль подання звернень та інтеграція YOLO** — Завантаження фото, геопозиція, запуск моделі YOLO (подвійний поріг: 15% та 85%), миттєва публікація для Співробітника.
* **Epic 4: Панель модерації дефектів (Back-office)** — Робоче місце модератора, модерація окремих рамок (боксів), логічне вимкнення шуму (`is_valid = false`), автоматичний перерахунок статусів.
* **Epic 5: Зворотний зв'язок, оцінка якості та аналітика** — Оцінка точності розпізнавання (UC-U6), аналітичні звіти та експорт датасету для донавчання.

---

## 2. Деталізація Epic 1: Базова інфраструктура та автентифікація

**Мета епіку:** Створити працездатний каркас застосунку (Backend + Frontend + DB), зв'язати їх через Docker Compose та реалізувати повний цикл автентифікації користувачів із фіксацією глобальної згоди на обробку даних.

### User Story 1.1: Контейнеризація середовища розробки
* **Опис:** Як розробник, я хочу розгорнути початковий каркас FastAPI, React та PostgreSQL через Docker Compose, щоб система запускалася єдиною командою на будь-якому комп'ютері.
* **Acceptance Criteria (Критерії приймання):**
  1. У корені репозиторію налаштовано робочий `docker-compose.yml`.
  2. Команда `docker-compose up` успішно піднімає три контейнери: `db` (Postgres 16), `backend` (FastAPI), `frontend` (React/Vite).
  3. Бекенд успішно перевіряє підключення до бази даних при старті.
  4. Доступні сторінки: Swagger UI (`http://localhost:8000/docs`) та стартова сторінка React (`http://localhost:3000`).

### User Story 1.2: Моделі даних користувача та міграції БД
* **Опис:** Як бекенд-інженер, я хочу створити структуру таблиці `User` та налаштувати міграції Alembic, щоб зберігати облікові записи та глобальну згоду на донавчання ШІ.
* **Acceptance Criteria:**
  1. Створено модель SQLAlchemy для таблиці `User` відповідно до ER-діаграми (`UUID`, `full_name`, `email`, `password_hash`, `role`, `training_consent`).
  2. Ролі обмежені значеннями ENUM: `citizen`, `worker`, `admin`.
  3. Налаштовано Alembic, перша міграція успішно створює таблицю в базі даних.

### User Story 1.3: Реєстрація нового користувача (API + UI)
* **Опис:** Як Гість, я хочу зареєструватися в системі, вказавши свої дані та обравши налаштування згоди на донавчання ШІ, щоб отримати роль Громадянина.
* **Acceptance Criteria:**
  1. Реалізовано ендпоінт `POST /api/auth/register`.
  2. Пароль хешується безпечним алгоритмом (bcrypt) перед збереженням у БД.
  3. Чекбокс «Дозволяю використовувати мої фото для донавчання моделі ШІ» коректно записує значення `true/false` у поле `training_consent`.
  4. На фронтенді реалізовано мобільну форму реєстрації згідно з мокапом `02-register.png`.
  5. Валідація: заборона дублювання email, довжина пароля не менше 8 символів.

### User Story 1.4: Автентифікація та сесії (JWT)
* **Опис:** Як зареєстрований користувач, я хочу увійти в систему за допомогою email та пароля, щоб отримати доступ до захищених функцій.
* **Acceptance Criteria:**
  1. Реалізовано ендпоінт `POST /api/auth/login`, що повертає пару JWT-токенів (Access та Refresh).
  2. У payload токена зберігаються `user_id` та `role`.
  3. На фронтенді реалізовано форму входу згідно з мокапом `03-login.png`.
  4. Токен зберігається на клієнті, реалізовано автоматичне підставлення токена в заголовок `Authorization: Bearer`.

### User Story 1.5: Керування профілем та згодою
* **Опис:** Як Громадянин, я хочу мати змогу переглянути свій профіль та змінити налаштування згоди на донавчання ШІ, щоб контролювати використання моїх даних.
* **Acceptance Criteria:**
  1. Реалізовано захищений ендпоінт `GET /api/users/me` для отримання даних поточного користувача.
  2. Реалізовано ендпоінт `PATCH /api/users/me` для перемикання прапорця `training_consent`.
  3. При зміні налаштування значення миттєво оновлюється в базі даних.
